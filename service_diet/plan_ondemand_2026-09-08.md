## 왜 사양 축소를 권하지 않는가

DocumentDB 의 r 계열 최소 사양은 `.large` 다. 그 아래는 `db.t4g.medium`(2vCPU/**4GB**) 뿐이라
**16GB → 4GB** 가 된다. 100MB 엑셀 처리 시 실패 위험이 크고, 검증하려면 대용량 부하시험이 필요하다.
절감액도 RI 보다 작다.

## 왜 B안(전체 온디맨드)을 권하지 않는가

ECS 를 0 으로 내리면 ALB 가 **503 을 반환**한다. 이용자는 "기동 중" 안내조차 못 보고
브라우저 오류를 만난다. 이를 피하려면 CloudFront 오류 페이지, 별도 기동용 API Gateway,
프론트엔드 재작성이 필요하다. **추가 절감 $80 을 위해 공수가 2배(2.5일 → 5.5일)가 되고
장애 지점이 여럿 늘어난다.**

# 3. E안 설계 — DB 온디맨드

## 3.1 구조

```
[이용자] → CloudFront → S3 (프론트, 항상 가동)
                     → ALB → ECS (항상 가동, 1대)
                                │
                                ├─ DB 정지 상태면 503 대신 "기동 중" 응답 + 기동 트리거
                                │
                                └→ DocumentDB  ← 정지/기동 대상
                                   ElastiCache (정지 불가, 상시)

[EventBridge 스케줄] → [Lambda: 유휴 판정·정지] → DocumentDB stop
                     → [Lambda: 자동재시작 감시]  → 재정지
```

**핵심**: 앱이 항상 떠 있으므로 기동 트리거와 상태 안내를 앱이 직접 처리한다.
새로 만들 것은 Lambda 2개와 EventBridge 규칙뿐이다.

## 3.2 기동 경로

1. 이용자가 접속 → 프론트엔드는 S3/CloudFront 에서 즉시 로드 (대기 없음)
2. 프론트가 API 호출 → 백엔드가 DocumentDB 연결 실패를 감지
3. 백엔드가 **503 대신 `{"status":"STARTING"}` 반환** + `start-db-cluster` 호출
4. 프론트가 "데이터베이스 기동 중 (예상 5~10분)" 화면과 진행 표시
5. 백엔드가 클러스터 `available` 을 폴링, 완료되면 정상 응답 재개

> 백엔드가 `docdb:StartDBCluster` 를 호출하려면 **태스크 역할에 권한 추가**가 필요하다.
> 남용을 막기 위해 대상 클러스터 ARN 으로 리소스를 한정한다.

## 3.3 정지 경로

EventBridge 가 30분마다 판정 Lambda 를 호출한다. **아래를 모두 만족할 때만** 정지한다.

| # | 조건 | 지표 |
|---|---|---|
| 1 | 최근 60분간 정상 응답 없음 | ALB `HTTPCode_Target_2XX_Count` = 0 |
| 2 | 진행 중 엑셀 작업 없음 | SQS `ApproximateNumberOfMessagesVisible` + `NotVisible` = 0 |
| 3 | 대시보드 생성 작업 없음 | Redis 진행률 키 부재 |
| 4 | DB 커넥션 유휴 | DocDB `DatabaseConnections` ≤ 기준선 |
| 5 | 클러스터가 `available` | 전이 중이면 건너뜀 |

**봇 트래픽은 자동으로 배제된다.** 봇은 98.6% 가 4XX 이므로 조건 1(2XX 기준)에 걸리지 않는다.
이 사실은 보고서 부록 A 에서 이미 검증됐고, 이번 30일 실측에서도 동일하다.

## 3.4 7일 자동 재시작 대응

AWS 는 정지 후 최대 7일에 클러스터를 자동 재시작한다. **이것이 이 방안의 가장 큰 운영 부담이다.**

- 감시 Lambda 가 30분마다 상태를 확인해, `available` 인데 유휴면 다시 정지한다
- 즉 7일마다 최대 30분의 가동 시간이 낭비된다 (월 약 2시간, 비용 영향 $0.7 수준)
- **자동 재시작 자체를 막을 방법은 없다.** AWS 정책이다

# 6. 권고

**단독으로는 RI 를, 절감폭이 우선이면 E안을 권한다. 둘은 병행할 수 없다** —
RI 는 사용 여부와 무관하게 예약 요금을 내므로, 정지해도 비용이 줄지 않는다.

## 판단 기준

| 상황 | 선택 |
|---|---|
| 서비스 존속이 **1년 이상 확정** + 응답성 우선 | **RI** — 월 $75~110, 위험 0, 반나절 |
| 존속 기간 미확정 또는 **절감폭 우선** | **E안** — 월 약 $200, 대기 5~10분, 2.5일 |
| 둘 다 부담 | **현행 유지** — 이미 27% 절감했다 |

## 의사결정에 필요한 것

1. **서비스 존속 기간이 1년 이상 확정되는가?** → RI 가능 여부를 가른다
2. **첫 접속 5~10분 대기를 이용자가 수용할 수 있는가?** → E안 가능 여부를 가른다
   - 실사용이 하루 1건, 월 12일이라 **대기를 겪는 횟수 자체는 월 12회 수준**이다
3. RI 실제 요율 — **콘솔에서만 확인 가능**하다 (아래 부록 A)

```

  → 0건

db.r8g.large 의 ProductDescription 목록
  → aurora-mysql, aurora-postgresql, mariadb, mysql, postgresql   (docdb 없음)

aws docdb describe-reserved-db-instances-offerings
  → 해당 명령 자체가 존재하지 않음
```

**콘솔 경로**: Amazon DocumentDB → Reserved instances → Purchase reserved instances
→ 인스턴스 클래스 `db.r8g.large`, 기간 1년, 결제 옵션(No Upfront / Partial / All Upfront) 비교

ElastiCache RI 는 CLI 로 확인된다 — `cache.t4g.micro` No Upfront $0.016/h, 월 약 $5.8 절감.
Fargate 는 Compute Savings Plans 로 약 20%(월 약 $17) 절감 가능하다.
**셋을 모두 적용하면 월 약 $100~130 절감**이며 이용자 영향은 0 이다.
