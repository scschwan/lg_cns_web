# 사후 발견 — 백엔드가 구 Redis 를 계속 쓰고 있었다 (2026-09-08 15:30)

## 발견 경위

"구 캐시를 지금 지워도 되는가" 를 판단하려고 양쪽 클러스터의 실사용 지표를 비교하다가
**예상과 정반대의 결과**가 나왔다.

| 클러스터 | 최근 3시간 GetTypeCmds | 기대 |
|---|---:|---|
| `finance-redis-cluster` (구) | **547** | 0 이어야 함 |
| `finance-redis-micro` (신) | 8 | 대부분이 여기여야 함 |

계정 내 컴퓨트를 전수 확인했으나(Lambda 2개, ECS 서비스 1개, 실행 중 EC2 0대)
모두 `REDIS_HOST` 가 micro 였다. task definition 264/265/266 의 값도 재확인했다.

## 원인

`backend/src/main/resources/application.yml:129` — **prod 프로파일에 구 클러스터가 하드코딩**돼 있었다.

```yaml
spring:
  config:
    activate:
      on-profile: prod
  data:
    redis:
      host: finance-redis-cluster.1kdayr.0001.apn2.cache.amazonaws.com   # ← 문제
```

공통 섹션(21행)은 `host: ${REDIS_HOST:localhost}` 로 올바르게 돼 있었으나,
**Spring 은 프로파일 설정이 공통 설정을 덮어쓴다.** 따라서 task-def 의 `REDIS_HOST`
환경변수 교체(1-C)는 **백엔드에 대해 아무 효과가 없었다.**

| 구성요소 | 실제 접속 대상 |
|---|---|
| 백엔드 (ECS) | ❌ `finance-redis-cluster` (구, t4g.small) |
| Lambda `ExcelCoordinator` / `ExcelWorker` | ✅ `finance-redis-micro` |

## 영향

1. **구 클러스터를 삭제했다면 백엔드 Redis 가 즉시 끊겼다.** 1주 존치 관행이 결과적으로 사고를 막았다.
2. **조치 3(ElastiCache 축소)의 $17.5 절감이 미실현**일 뿐 아니라, micro 가 순수 추가 비용으로만
   붙어 두 클러스터 요금을 동시에 내고 있었다.
3. **캐시가 둘로 분리**돼 있었다. 백엔드는 구 클러스터, Worker 는 micro 에 쓴다.
   계획서가 경고한 "백엔드만 바꾸면 진행률이 깨진다" 의 정반대 형태다.
   금일 업로드가 정상이었던 것은 진행률을 백엔드가 자체 관리했기 때문으로 보이나,
   잠재 결함이 남아 있던 상태다.

## 조치

- `application.yml` prod 프로파일
  - `host:` 하드코딩 → `${REDIS_HOST:localhost}`
  - `port:` → `${REDIS_PORT:6379}` 로 통일
  - 같은 실수를 막는 주석 추가
- prod 프로파일 전체 재점검 — 다른 하드코딩 없음 (`MONGODB_URI` 는 2단계에서 이미 정리)
- 재배포 `v1.1.317`

## 교훈

**환경변수 교체는 "task-def 에 반영됐다" 로 검증이 끝나지 않는다.**
소스의 프로파일 설정이 덮어쓸 수 있으므로, **대상 리소스의 실사용 지표로 확인**해야 한다.
1단계 당시 `CurrConnections` 가 양쪽 모두 유휴 baseline 이라 판별 불가라고 기록했는데,
`GetTypeCmds`/`KeyBasedCmds` 같은 **명령 처리량 지표**를 봤다면 그때 발견할 수 있었다.
