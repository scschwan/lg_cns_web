# 유휴 리소스 정리 — 상세 설계

> `plan.md` 의 실행 단계 1~3에 해당하는 구현 설계서.
>
> **본 계획은 서비스를 상시 가동한 채 유휴 리소스만 정리한다.** 신규 컴포넌트를 만들지 않으며, 백엔드 변경은 설정 2개와 코드 1줄에 그친다.
>
> 채택하지 않은 온디맨드 설계는 **부록 A**에 보존한다(향후 재검토용).

## 2. 1단계 — 즉시 조치 (1시간)

### 2.1 ECS 태스크 2대 → 1대

```powershell
aws ecs update-service --cluster finance-cluster --service finance-api --desired-count 1
```

배포 설정이 `minimumHealthyPercent 100 / maximumPercent 200` 이므로 무중단으로 반영된다. 타겟그룹 `deregistration_delay 120초` 로 연결 드레이닝이 수행된다.

**근거**: CPU 평균 0.13%(최대 52%), 메모리 9.3%, 하루 정상 요청 12건. 이중화의 실익이 없다.

**대가**: 태스크 장애 시 자동 재기동까지 1~2분 이용 불가. 실사용 빈도를 고려하면 겹칠 확률이 낮다.

### 2.2 ElastiCache `t4g.small` → `t4g.micro`

**노드 타입 변경은 신규 생성 후 엔드포인트 전환 방식으로 한다.** 진행률·캐시 데이터는 유실되나 TTL 기반 임시 데이터라 무해하다.

| 순서 | 작업 |
|:-:|---|
| 1 | `cache.t4g.micro` 신규 클러스터 생성 (`backend/create-redis-cluster.ps1` 참고, 동일 서브넷·SG) |
| 2 | **`REDIS_HOST` 를 3곳에서 동시 교체** — `task-def-template.json:40`, Lambda `ExcelCoordinator`, Lambda `ExcelWorker` |
| 3 | 배포 → 업로드 진행률 표시 정상 확인 |
| 4 | 구 클러스터 **1주 존치** 후 삭제 |

> ⚠️ **Lambda 2개도 `REDIS_HOST` 를 사용한다.** 백엔드만 바꾸면 엑셀 처리 진행률이 깨진다.

**근거**: 메모리 사용률 0.88%(1.37GB 중 약 12MB), CPU 2.2%, 연결 5개. `t4g.micro`(0.5GB)로도 10배 여유.

**사후 검증**: 전환 2주 후 `DatabaseMemoryUsagePercentage` 가 60% 미만인지 확인한다.

### 2.3 백엔드 설정 변경

| 파일 | 항목 | 현재 | 변경 | 근거 |
|---|---|---|---|---|
| `task-def-template.json` | `stopTimeout` | 없음(기본 30초) | **120** | graceful shutdown 시간 확보 (Fargate 상한) |
| `task-def-template.json` | `healthCheck.startPeriod` | 120 | **45** | 실측 기동 17~23초 |
| `application.yml` | `server.shutdown` | 없음 | **graceful** | |
| `application.yml` | `spring.lifecycle.timeout-per-shutdown-phase` | 없음 | **110s** | stopTimeout 120초보다 짧게 |
| `DashboardGenerationService.java:55` | `t.setDaemon(true)` | daemon | **`false`** | **이 한 줄이 없으면 위 설정이 무의미** |

**`setDaemon` 을 바꾸는 이유**: daemon 스레드는 JVM 종료 시 즉사한다. SIGTERM 을 받으면 진행 중인 대시보드 생성이 그 자리에서 죽는다. non-daemon 으로 바꿔야 JVM 이 스레드 종료를 기다린다.

> `ClusteringService`, `SessionDataService`, `UploadService` 의 executor 는 이미 non-daemon 이므로 변경 불필요.
> `DbThrottleConfig.java` 의 `Semaphore(10)` 도 변경 불필요 — desired=1 이 되면 인스턴스 로컬 = 클러스터 전체가 되어 오히려 의미가 정확해진다.

**1단계에 포함하는 이유**: 어차피 task-def 를 수정하고 재배포하므로 함께 적용하면 **2·3단계 재배포에서 진행 중 작업이 보호된다.**

## 4. 3단계 — NAT Gateway 제거 (0.5일)

### 4.1 NAT 트래픽의 정체 (측정 확인)

태스크 재기동일마다 `BytesOutToSource` 가 292~302MB 발생하며, 이는 **ECR 이미지 155MB × 태스크 2개**와 일치한다. 태스크 1개만 재시작된 날은 136~146MB 다.

| 통신 경로 | 현재 | 조치 후 |
|---|---|---|
| ECS → ECR | NAT | 퍼블릭 서브넷 → **IGW** |
| ECS → CloudWatch Logs | NAT | 퍼블릭 서브넷 → **IGW** |
| Lambda → S3 (`ExcelCoordinatorHandler:165`, `ExcelWorkerHandler:129`) | NAT | **S3 Gateway Endpoint** ✅ 완료 |
| Lambda → SQS (`ExcelCoordinatorHandler:227` `sendMessage`) | NAT | **SQS Interface Endpoint** |
| Lambda → DocDB / Redis | VPC 내부 | 변경 없음 |

> `ExcelWorkerHandler` 는 SqsClient 를 갖지 않는다 — 이벤트 소스 매핑으로 수신만 하므로 Lambda 서비스가 폴링한다. Lambda 코드에 외부 HTTP 호출은 없다.
> **CloudWatch Logs 엔드포인트는 불필요하다** — Lambda 로그는 고객 ENI 가 아닌 Lambda 서비스가 직접 전송한다.

| 순서 | 작업 | 검증 |

**롤백**: NAT 재생성(5분) + `finance-private-rt`(`rtb-021492a36dbdbfb3b`) 의 `0.0.0.0/0` 라우트 복구 + ECS network config 원복.

# 부록 A. 온디맨드 전환 설계 (채택하지 않음)

> 이용자 대기와 운영 복잡도를 이유로 채택하지 않았으나, 설계와 검증 결과를 보존한다. 향후 재검토 시 그대로 활용할 수 있다.

## A.1 유휴 판정 — 백엔드 코드 없이 가능

**봇 트래픽은 ALB 메트릭이 이미 분리해준다.** 30일간 봇 요청 146,743건은 **전부 4XX** 이고 정상 요청 356건은 2XX 다. `HTTPCode_Target_2XX_Count` 만 보면 봇이 자동 배제된다.

```
종료 = (2XX 합계(24h) == 0)
   AND (ECS CPUUtilization Max(1h) < 10%)
   AND (SQS Visible + NotVisible == 0)
```

| 지표 | 네임스페이스 | 역할 |
|---|---|---|
| `HTTPCode_Target_2XX_Count` (Sum) | `AWS/ApplicationELB` | 주 판정 |
| `CPUUtilization` (Maximum) | `AWS/ECS` | 보조. **임계값 10%** |
| `ApproximateNumberOfMessages{Visible,NotVisible}` | `AWS/SQS` | 엑셀 처리(최대 15분) 보호 |

**CPU 임계값 근거** (60일 실측): 평상시 최대 0.3~2.4%, 실사용일 4.20%, 대용량 작업일 52.61%. 5% 로 잡으면 경량 사용일과 겹친다.

**메트릭 결측은 유휴로 간주**하여 비용 폭주를 막는다. **최대 연속 가동 72시간** 상한으로 탭 방치 시나리오를 커버한다.

## A.2 선기동(Prefetch) — 봇이 유발하지 않는 근거

| 경로 | 30일 요청 |
|---|---:|
| ALB 직접 | 146,743건 |
| **CloudFront (React 앱 로드)** | **1,906건** |

봇은 **ALB 도메인을 직접 스캔**하며 CloudFront 로는 거의 오지 않는다. 스캐너는 대부분 JS 를 실행하지 않는다. 따라서 React 로드 시점에 자동으로 wake 를 호출해도 안전하다.

프론트 구현은 `services/wakeService.js` 신규 + 앱 진입점에 `useEffect(() => { prefetchWake(); }, [])` 1줄. **raw axios 를 써야 한다** — `api.js` 인터셉터(:112-115)가 토큰 부재 시 `/login` 리다이렉트를 하기 때문이다.

## A.3 wake Lambda

**Lambda Function URL** 을 쓴다. 무료이고 VPC 외부라 NAT 가 불필요하며, CloudFront/ALB 와 분리되어 백엔드가 0대여도 동작한다. API Gateway 는 **통합 타임아웃 30초 상한**이 있어 6분 동기 병합이 파손되므로 기각했다.

| 경로 | 동작 |
|---|---|
| `POST /wake` | 토큰 검증 → `ecs:UpdateService desired=1` (멱등) |
| `GET /status` | ECS runningCount + ALB 타겟 health |
| (EventBridge 5분) | `reconcile` — 종료 조건 충족 시 `desired=0` |

**dry-run 모드**(`SCALE_IN_ENABLED=false`)로 2~3일 관찰 후 실적용한다.

## A.4 CloudFront 5xx 캐싱 함정

CloudFront 는 오리진 5xx 를 **기본 10초 캐싱**한다. 기동 직후 첫 요청이 캐시된 503 을 받아 안내가 다시 뜨는 루프가 생기므로, `CustomErrorResponses` 에 502/503/504 를 `ErrorCachingMinTTL=0` 으로 등록해야 한다. (현재 배포는 미설정 상태)

## A.5 DocumentDB 정지·기동 (B안 전용)

**API 는 실재한다.** 서버리스 상품은 없으나 `stop-db-cluster` / `start-db-cluster` 를 명시적으로 호출하는 방식은 가능하며, 전제 조건(`Status: available`, `GlobalClusterIdentifier: null`, Elastic 아님)을 모두 충족한다.

**핵심 난점 — 기동 순서 제어**: `management.health.mongo.enabled: false` 때문에 **DocDB 가 정지 상태여도 `/actuator/health` 는 200 을 반환**한다. 동시에 올리면 ECS 가 먼저 healthy 가 되어 사용자가 진입하고 모든 화면이 500 을 뱉는다.

| 방식 | 대기 | 리스크 |
|---|---|---|
| 순차 기동 (DB `available` 확인 후 ECS) | 7~13분 | 없음 |
| `mongo.health` 활성화 → 동시 기동 | 5~10분 | 평상시 DB 순단 시 **재시작 루프** |

**기타 제약**: 최대 7일 후 자동 재시작(EventBridge 일 1회 재-정지로 대응), 정지 중 인스턴스 요금 0이나 스토리지·백업 약 $4.6/월 지속, 재기동 시 `InsufficientDBInstanceCapacity` 가능(단 `db.r8g.large` 가 3개 AZ 모두 지원되고 서브넷 그룹도 3AZ 라 확률 낮음).

**IAM 은 `docdb:` 가 아니라 `rds:StartDBCluster` / `rds:StopDBCluster`** 다.

## A.6 로그인/목록 Lambda (D안 전용)

체감 대기를 0에 수렴시키려면 `POST /api/auth/login`(`AuthService.login()` 약 40줄)과 `GET /api/projects`(`ProjectController:58`)를 Lambda 에 중복 구현한다. 공수 2.5일.

**가장 중요한 검증은 JWT 상호 호환성**이다. `JwtTokenProvider:48-49` 의 `Keys.hmacShaKeyFor(secret.getBytes())` 와 동일한 서명 키·클레임·만료 정책을 써야 백엔드가 Lambda 발급 토큰을 인정한다. Secrets Manager 를 단일 출처로 참조한다.

`backend/lambda/` 에 Java 21 프로젝트가 이미 있어 `mongodb-driver-sync`, `gson`, `MongoDBConfig.java` 를 재사용할 수 있다. **JJWT 와 BCrypt 의존성 추가가 필요**하다.

# 부록 B. 진행률 외부화 (별도 과제)

> 비용과 무관하나 **desired=2 인 현재도 재현되는 버그**다. 1단계로 태스크가 1대가 되면 증상은 자연 해소되나 근본 수정은 별도로 필요하다.

4개 `ConcurrentHashMap` 이 태스크 로컬 메모리에 진행률을 보관한다.

| 대상 | 위치 |
|---|---|
| `mergeProgressMap`, `sessionMergeMap`, `sessionBatchMergeMap` | `ClusteringService.java:615/618/621` |
| `statusMap` | `DashboardGenerationService.java:50` |

폴링이 다른 태스크로 라우팅되면 `NOT_FOUND` 가 반환된다. `PROGRESS_RETAIN_MS = 30_000`(:634)은 인스턴스 고정을 전제하는데 ALB 는 그것을 보장하지 않는다.

반면 `ExportService.java:1077` 은 이미 "진행률은 Redis Hash 에 저장하여 서버 재시작에도 안전"하다고 주석에 명시하며 올바른 패턴을 구현해 두었다. **`RedisService.java:181-243` 의 `saveCompleteProgress` / `lockSessionComplete` 패턴을 나머지 4곳에 복제하면 된다.**

| 상수 | 키 패턴 | TTL |

| `MERGE_PROGRESS_PREFIX` | `merge:progress:<taskId>` | 1h (완료 시 5m) |
| `SESSION_MERGE_PREFIX` | `merge:session:<sessionId>` | 1h |
| `BATCH_MERGE_PREFIX` | `merge:batch:<sessionId>` | 1h |
| `DASHGEN_PREFIX` | `dashgen:status:<projectId>` | 1h |
