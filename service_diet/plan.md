### 1.3 NAT Gateway 제거가 지금 불가능한 이유

ECS 태스크가 프라이빗 서브넷(`subnet-08cdb7f10fd2f72f4`, `subnet-0bfa6431b2de4c627` → `rtb-021492a36dbdbfb3b`)에 있고, 기본 경로가 **NAT Gateway 전용**이다. IGW 경로가 없다.

지금 삭제하면 **ECR 이미지 pull과 CloudWatch Logs 전송이 끊겨** 태스크 재시작 시 복구 불가 상태가 된다.

**실측 증거** — `BytesOutToSource`(인터넷→VPC) 일별 추이:

| 날짜 | 5/19 | 6/9 | 6/20 | 6/30 | 7/1 | 7/6 | 7/25 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 다운로드 | 292.4MB | 292.3MB | 295.4MB | 146.5MB | 294.8MB | 136.7MB | 301.8MB |

**ECR 이미지 155MB × 태스크 2개 = 약 310MB**와 일치한다. 146MB·136MB는 태스크 1개만 재시작된 경우다. NAT가 ECR 이미지 수신 경로로 **실제 사용되고 있음이 측정으로 확인된다.**

#### 제거 가능 조건 (3단계에서 충족)

| 통신 경로 | 현재 | 조치 후 |
|---|---|---|
| ECS → ECR / CloudWatch Logs | NAT | **퍼블릭 서브넷 이동 → IGW** |
| Lambda → S3 (`ExcelCoordinatorHandler:165`, `ExcelWorkerHandler:129`) | NAT | **S3 Gateway Endpoint** ✅ 완료 |
| Lambda → SQS (`ExcelCoordinatorHandler:227` `sendMessage`) | NAT | **SQS Interface Endpoint** ⬅ 미생성 |
| Lambda → DocDB / Redis | VPC 내부 | 변경 없음 |

> `ExcelWorkerHandler`는 SqsClient를 갖지 않는다 — 이벤트 소스 매핑으로 수신만 하므로 Lambda 서비스가 폴링한다. Lambda 코드에 외부 HTTP 호출은 없다.

**판정 기준**: 선행 조치 후 재배포 1회를 수행하고 `BytesOutToSource`가 **0**으로 유지되면 안전하게 삭제한다.

## 2. 확정 방침

### 2.1 서비스는 상시 가동한다

미사용 시 서버를 정지하는 온디맨드 방식은 **채택하지 않는다.**

| 사유 | 내용 |
|---|---|
| 이용자 대기 발생 | 애플리케이션 서버만 정지해도 재기동 1.5~3분, 데이터베이스까지 정지하면 7~13분 |
| 사용 시간대 불규칙 | 실측상 새벽 2시·저녁 7시. 해당 시간대 이용자에게 대기는 부담이 큼 |
| 운영 복잡도 급증 | 기동 트리거·유휴 판정·자동 정지·진행 중 작업 보호 등 신규 구성요소 다수 |
| 신규 장애 요인 | 자원 확보 실패, 기동 순서 문제, 판정 오탐 등 기존에 없던 리스크 발생 |

**유휴 리소스 정리만으로 28%를 절감할 수 있으며, 이용자 영향은 사실상 없다.** 온디맨드 검토 결과는 향후 참조를 위해 **부록 A**에 보존한다.

### 2.2 데이터베이스는 현행 유지 (사양·가동 모두)

6개월 지표상 CPU **최대 100%**, 연결 **최대 287**, 여유 메모리 3.14GB(16GB 중 12.8GB 사용). 100MB 엑셀 처리 시 실패 위험이 크므로 **사양 축소도 하지 않는다.**

### 2.3 예약 할인은 이번 범위에서 제외

상시 가동이 확정되면 예약 인스턴스(RI)·Savings Plans로 추가 절감이 가능하나, **1년 약정으로 중도 해지가 불가**하다. 서비스 존속 기간이 확정되지 않아 이번 범위에서 제외한다. 검토 자료는 **부록 B**에 보존한다.

### 4.1 백엔드 변경 (최소) — 1단계에 포함

| 파일 | 변경 | 성격 |
|---|---|---|
| `backend/task-def-template.json` | `"stopTimeout": 120` 추가, `startPeriod` 120 → 45, `REDIS_HOST` 교체 | 설정 |
| `backend/src/main/resources/application.yml` | `server.shutdown: graceful` | 설정 |
| `DashboardGenerationService.java:55` | `setDaemon(true)` → `false` | **코드 1줄** |

`setDaemon`만 바꾸는 이유: 현재 daemon 스레드라 SIGTERM에 즉사한다. graceful shutdown을 켜도 이 한 줄이 없으면 무의미하다.

**1단계에 넣는 이유**: 어차피 task-def를 수정하고 재배포하므로 함께 적용하면 **2·3단계 재배포에서 진행 중 작업이 보호된다.** `startPeriod` 45초는 실측 기동 시간 17~23초에 근거한다.

### 4.2 NAT 제거 순서 (3단계, 순서 엄수)

1. **SQS Interface Endpoint 생성** (`private-subnet-1a` 1개 AZ, 약 $9.2/월)
2. ~~S3 Gateway Endpoint~~ — **완료** (`vpce-0fdf46f2c2ce0a2b9`, 무료)
3. **ECS를 퍼블릭 서브넷 + `assignPublicIp=ENABLED`로 이동**
   - `finance-ecs-sg`(`sg-0b2f80b067408e320`) 인바운드는 ALB SG(`sg-03100bb81c51586d0`) 단일 규칙이므로 퍼블릭 IP를 붙여도 외부 접근 불가
   - ALB 타겟 그룹은 target-type `ip`이며 태스크 프라이빗 IP로 등록되므로 동작 변화 없음
4. **검증**: 재배포로 ECR pull 성공, 엑셀 업로드 E2E, CloudWatch 로그 수신 확인
5. **제거 안전 판정**: 재배포 1회 후 `BytesOutToSource`가 **0**으로 유지되는지 확인
6. NAT 삭제 → EIP `release-address`

> **Lambda는 VPC를 벗어날 수 없다** (DocumentDB·ElastiCache 접근 필요). 그래서 엔드포인트로 대체한다.
> **CloudWatch Logs 엔드포인트는 불필요하다** — Lambda 로그는 고객 ENI가 아닌 Lambda 서비스가 직접 전송한다.
> ⚠️ 미연결 EIP도 과금되므로 `release-address`를 반드시 실행한다.

### 4.3 단계별 사용자 영향 (전환 작업 중)

배포 설정이 `minimumHealthyPercent 100 / maximumPercent 200`, 타겟그룹 `deregistration_delay 120초`이므로 **모든 단계가 HTTP 요청 단위로 무중단**이다. 배포 실패 시 circuit breaker가 자동 롤백한다.

| 단계 | HTTP 중단 | 재배포 | 실제 영향 |
|:--:|:-:|:-:|---|
| 1 | 없음 | 1회 | **가용성 2대→1대 (영구)** · Redis 교체로 진행률 캐시 초기화 |
| 2 | 없음 | 1회 | **전체 사용자 강제 로그아웃 (확정)** — JWT 서명 키 교체 |
| 3 | 없음 | 1회 | 없음 (태스크 IP 변경은 ALB가 흡수) |

**완화책**: 재배포 3회를 **비사용일에 수행**한다(실사용일 월 4일). 2단계 강제 로그아웃은 회피 불가하나 사전 공지로 대응한다.

## 6. 검증 방법

1. **1단계 후** — CloudFront 접속 → 로그인 → 프로젝트 조회 정상. ALB 타겟 healthy **1개**. **업로드 진행률 표시 정상**(Redis 엔드포인트 교체 검증). 3일 후 Cost Explorer 일 비용 하락 확인.
2. **2단계 후** — 신규 JWT로 로그인 성공, 기존 토큰 거부 확인. DocDB 신규 비밀번호로 **백엔드·Lambda 양쪽** 연결 확인.
3. **3단계 후** — 엑셀 업로드 E2E(S3→Coordinator→SQS→Worker→Mongo), 재배포로 **ECR pull 성공**, CloudWatch 로그 수신, `finance-ecs-sg`에 0.0.0.0/0 인바운드 부재 재확인. **`BytesOutToSource`가 0인지 확인한 뒤에만 NAT 삭제.**
4. 전환 후 1개월간 주 1회 Cost Explorer 확인.

# 부록 A. 온디맨드 전환 검토 결과 (채택하지 않음)

> 향후 재검토를 위해 보존한다. 세 가지 안을 설계·검증했으며, 이용자 대기와 운영 복잡도를 이유로 모두 채택하지 않았다.

| 구분 | B안: 전체 온디맨드 | C안: 앱만 온디맨드 | D안: C안 + 로그인 분리 |
|---|---|---|---|
| 데이터베이스 | 미사용 시 정지 | 상시 유지 | 상시 유지 |
| 월 비용 | $111 (81% 절감) | $343 (42%) | $343 (42%) |
| **첫 접속 대기** | **7~13분** | **30~60초** | 거의 없음 |
| 기동 직후 성능 | 저하 (캐시 적중률 6.28%) | 변화 없음 | 변화 없음 |
| 공수 | 5.5일 | 4.5일 | 7일 |

## A.1 검증된 사실 (재검토 시 활용 가능)

- **DocumentDB stop/start API는 실재한다.** 서버리스 상품은 없으나 명시적 호출 방식은 가능하며, 클러스터 전제 조건(`Status: available`, 글로벌 클러스터 아님, Elastic 아님)을 모두 충족한다. 단 **최대 7일 후 자동 재시작**되며 AWS는 개발·검증 환경 용도로 안내한다.
- **정지 중 인스턴스 요금은 0**이 되고 스토리지·백업만 약 $4.6/월 발생한다(AWS 정책 기준, 본 계정 실증 없음).
- **봇은 CloudFront가 아니라 ALB를 직접 스캔한다**(146,743건 대 1,906건). 따라서 React 로드 시점 자동 기동 트리거가 안전하다.
- **유휴 판정은 백엔드 코드 없이 가능하다.** 봇 트래픽이 전부 4XX이므로 `HTTPCode_Target_2XX_Count`만 보면 자동 배제된다. 보조 지표로 ECS CPU(임계값 10%)와 SQS 큐 깊이를 쓴다.
- ECS CPU 실측: 평상시 최대 0.3~2.4%, 실사용일 4.20%, 대용량 작업일 52.61%.

## A.2 채택하지 않은 이유

1. **이용자 대기 발생** — 사용 시간대가 새벽 2시·저녁 7시로 불규칙해 대기 부담이 크다.
2. **운영 복잡도 급증** — 기동 트리거, 유휴 판정, 자동 정지, 진행 중 작업 보호 등 신규 구성요소가 다수 필요하다.
3. **신규 장애 요인** — 자원 확보 실패, 기동 순서 문제, 판정 오탐 등 기존에 없던 리스크가 생긴다.
4. **절감 대비 효용** — 유휴 리소스 정리만으로 28%를 확보할 수 있고, 온디맨드는 그 위에 14~53%p를 더하는 대가로 위 세 가지를 감수해야 한다.

# 부록 B. 예약 할인 검토 결과 (이번 범위 제외)

> 상시 가동이 확정되면 적용 가능한 절감 수단이다. **1년 약정으로 중도 해지가 불가**하여 서비스 존속 기간이 확정된 뒤 검토한다.

| 대상 | 현재 | 1년 약정 | 절감/월 | 확인 상태 |

| Fargate (Compute Savings Plans) | $84.50 | 약 $67.60 | 약 $17 | 제도 존재, 요율 확인 필요 |
| DocumentDB | $247.64 | 약 $161 (30% 가정) | 약 $86 | ⚠️ **확인 필요** |

**DocumentDB RI는 CLI로 조회되지 않았다.** `rds describe-reserved-db-instances-offerings`의 `ProductDescription` 목록에 `docdb`가 없고, r8g/r7g/r6g/r5 전 클래스에서 offering이 0건이다. 최신 세대에 미제공이거나 조회 경로가 다를 수 있어 **콘솔 확인이 필요하다.**

모두 적용 시 월 약 **$320 (46% 절감)** 으로 추정되며, 이는 온디맨드 C안($343)보다 저렴하면서 **이용자 영향이 0**이다. 서비스 존속이 1년 이상 확정되면 우선 검토할 가치가 있다.
