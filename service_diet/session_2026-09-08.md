## 4. 핵심 교훈

### 환경변수 교체는 task-def 확인으로 끝나지 않는다

1단계에서 `REDIS_HOST` 를 micro 로 바꾸고 "task-def 에 반영됨" 까지 확인한 뒤 완료로 보고했다.
그러나 `application.yml` prod 프로파일이 이를 덮어써 **백엔드는 오후까지 구 클러스터를 쓰고 있었다.**
Spring 은 프로파일 설정이 공통 설정을 이긴다.

발견 경위는 "구 캐시를 지금 지워도 되는가" 를 판단하려고 양쪽 지표를 비교한 것이었고,
**예상과 정반대의 결과**(구 547건 / micro 8건)가 단서였다.

> **검증은 대상 리소스의 실사용 지표로 한다.** `CurrConnections` 는 유휴 baseline 때문에
> 판별에 못 쓴다. `KeyBasedCmds` / `GetTypeCmds` 같은 **명령 처리량 지표**를 볼 것.

### 1주 존치 관행이 사고를 막았다

계획서의 "구 클러스터 1주 존치" 는 되돌릴 수단 확보용 관행이었는데,
결과적으로 위 결함이 드러날 시간을 벌어줬다. 즉시 삭제했다면 백엔드 Redis 가 끊겼다.

### 계획서 전제도 실측으로 재확인해야 한다

NAT 통과량이 계획서의 "재기동일마다 292~302MB" 가 아니라 **실측 약 0.5MB** 였다.
계획서 수치는 S3 Gateway Endpoint 생성 **이전** 측정치이고, ECR 레이어는 이미
엔드포인트로 빠져 NAT 로는 API 호출만 남아 있었다.
(요금의 97% 가 시간당 유휴 요금이므로 절감 결론 자체는 유효했다.)

## 5. 검증 방법

### E2E — 엑셀 업로드 1건으로 3단계를 동시 검증

세 단계에 걸쳐 미검증으로 남아 있던 항목이 한 번에 해소됐다.

| 검증 대상 | 근거 |
|---|---|
| Redis 전환 (1단계) | 백엔드의 `RedisConnectionUtils` 반복 접속, 진행률 폴링 정상 |
| JWT 키 교체 (2단계) | 신규 키로 재로그인 성공 / 구 서명키 토큰 **401 거부** |

| 파이프라인 전 구간 | 백엔드 → S3 → Coordinator → SQS → Worker → Mongo 완주 |

```
Coordinator  6,271행 인식 -> 데이터 6,270행, 청크 1개, Duration 2.0초
Worker       6,270건 삽입 / 22개 컬럼 / 100%, Duration 15.9~19.3초
             Max Memory 278MB (1024MB 중)
```

**NAT 삭제 전후로 2회 수행**했다. 삭제 전에는 NAT 우회가 가능해 엔드포인트 검증이 되지 않으므로,
삭제 후 재수행으로 SQS·S3 엔드포인트 경유를 실증했다.

## 11.4 후보안

### E안 — DB 온디맨드 (앱 상시 가동)

DocumentDB 만 정지/기동하고 ECS·ALB·Redis 는 상시 가동한다.
ECS 가 이미 $83 로 저렴하므로 **기동 트리거와 상태 안내를 담당하는 상시 지점**으로 쓴다.

- 절감 월 약 **$200** ($430 → $230), 공수 **2.5일**
- 신규 구성요소는 Lambda 2개와 EventBridge 규칙뿐
- B안처럼 ECS 를 0 으로 내리면 ALB 가 503 을 반환해 안내 화면조차 띄울 수 없다

### F안 — E안 + 로그인/조회 미러 (사용자 제안)

DocumentDB 정지 중에도 로그인과 프로젝트 목록이 동작하게 해 **"서버가 뻗었다"는 인상을 없앤다.**

**사용자 원안에서 수정한 부분**

| 원안 | 문제 | 수정 |
|---|---|---|
| ECS Fargate 내장 PostgreSQL | Fargate 임시 스토리지는 태스크 재시작 시 소멸. 재배포마다 데이터 유실. DocDB 정지 중 태스크가 재시작되면 미러를 채울 원본이 없어 로그인 불가(닭과 달걀) | **DynamoDB 미러** — 서버리스, 항상 가용, 이 규모면 월 $1 미만 |
| 엑셀 작업을 큐에 담아두기 | SQS 는 이미 있으나 현재 설정(VisibilityTimeout 1800초, maxReceiveCount 3)이면 **30분 지연** 후 재시도, 3회 실패 시 DLQ | **Lambda 이벤트 소스 매핑을 비활성화**. 메시지는 큐에 그대로 있다가 DB 기동 후 활성화 시 즉시 처리 |

**추가 설계 사항**
- DocDB 정지 중에는 **읽기 전용 모드**. 쓰기를 허용하면 기동 후 데이터가 갈라진다
  - 로그인, 프로젝트 목록 조회 → 미러에서 처리
  - 마지막 로그인 시각·감사 로그 → DocDB 기동 후 반영
  - 프로젝트 생성·수정·데이터 조회 → "기동 중" 안내
- 절감액은 E안과 **동일($200)**. F안은 순수 UX 개선이며 공수만 +1.5일 (총 약 4일)

## 11.5 정지/기동 실측 (2026-09-08 17:53~)

| 구간 | 시각 | 소요 |
|---|---|---|
| STOP 요청 → `stopped` | 17:53:15 → 18:00:42 | **7분 27초** |
| START 요청 → `available` | 18:01:02 → (측정 중) | (측정 중) |

**정지 중 앱 동작 — 설계상 중요한 확인 2건**

1. **ECS 가 태스크를 재시작하지 않는다.** `management.health.mongo.enabled: false` 라
   헬스체크가 DB 와 무관하게 200 을 반환하고 ALB 타겟이 healthy 로 유지된다.
   Mongo 헬스체크가 켜져 있었다면 **DB 정지 → 헬스체크 실패 → 태스크 무한 재시작** 악순환에
   빠졌을 것이다. 온디맨드의 필수 전제인데 이미 충족돼 있다.
2. **드라이버가 자동 재연결을 시도한다.** `MongoSocketOpenException: Connection refused` 가
   로그에 쌓이지만 `ServerMonitor` 스레드가 계속 재시도하며 프로세스는 정상이다.

정지에만 7분 27초가 걸린 점으로 미루어 기동도 짧지 않을 것으로 보인다.

## 11.6 판단 기준

기동 시간 실측값에 따라 E안·F안을 결정한다.

| 실측 기동 시간 | 판단 |
|---|---|
| 3분 이내 | 진행 화면만으로 충분. **F안 불필요** |
| 5~8분 | 경계선. 진행 화면 품질에 달렸다 |
| 10분 초과 | **F안 가치가 커진다.** 그 시간을 빈 화면으로 두기 어렵다 |

> "서버가 뻗었다" 는 인상을 없애는 것은 **온디맨드 방식과 무관하게 기동 중 화면을 제대로
> 만드느냐**의 문제다(프론트 0.5일). E안도 ECS 가 상시 가동이므로 즉시 응답하고 진행 상태를
> 보여줄 수 있다. F안이 추가로 사는 것은 **대기 중 자기 프로젝트 목록을 볼 수 있다**는 것 하나다.
