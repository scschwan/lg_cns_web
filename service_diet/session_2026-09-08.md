## 4. 핵심 교훈

### 환경변수 교체는 task-def 확인으로 끝나지 않는다

1단계에서 `REDIS_HOST` 를 micro 로 바꾸고 "task-def 에 반영됨" 까지 확인한 뒤 완료로 보고했다.
그러나 `application.yml` prod 프로파일이 이를 덮어써 **백엔드는 오후까지 구 클러스터를 쓰고 있었다.**
Spring 은 프로파일 설정이 공통 설정을 이긴다.

발견 경위는 "구 캐시를 지금 지워도 되는가" 를 판단하려고 양쪽 지표를 비교한 것이었고,
**예상과 정반대의 결과**(구 547건 / micro 8건)가 단서였다.

> **검증은 대상 리소스의 실사용 지표로 한다.** `CurrConnections` 는 유휴 baseline 때문에
> 판별에 못 쓴다. `KeyBasedCmds` / `GetTypeCmds` 같은 **명령 처리량 지표**를 볼 것.

### 1주 존치 관행이 사고를 막았다

계획서의 "구 클러스터 1주 존치" 는 되돌릴 수단 확보용 관행이었는데,
결과적으로 위 결함이 드러날 시간을 벌어줬다. 즉시 삭제했다면 백엔드 Redis 가 끊겼다.

### 계획서 전제도 실측으로 재확인해야 한다

NAT 통과량이 계획서의 "재기동일마다 292~302MB" 가 아니라 **실측 약 0.5MB** 였다.
계획서 수치는 S3 Gateway Endpoint 생성 **이전** 측정치이고, ECR 레이어는 이미
엔드포인트로 빠져 NAT 로는 API 호출만 남아 있었다.
(요금의 97% 가 시간당 유휴 요금이므로 절감 결론 자체는 유효했다.)

## 5. 검증 방법

### E2E — 엑셀 업로드 1건으로 3단계를 동시 검증

세 단계에 걸쳐 미검증으로 남아 있던 항목이 한 번에 해소됐다.

| 검증 대상 | 근거 |
|---|---|
| Redis 전환 (1단계) | 백엔드의 `RedisConnectionUtils` 반복 접속, 진행률 폴링 정상 |
| JWT 키 교체 (2단계) | 신규 키로 재로그인 성공 / 구 서명키 토큰 **401 거부** |
| DocDB 비밀번호 · 백엔드 | `MongoTemplate` 조회 정상, ERROR 0건 |
| DocDB 비밀번호 · Lambda Worker | **`MongoDB 삽입 완료: 6270건`** |
| 파이프라인 전 구간 | 백엔드 → S3 → Coordinator → SQS → Worker → Mongo 완주 |

```
Coordinator  6,271행 인식 -> 데이터 6,270행, 청크 1개, Duration 2.0초
Worker       6,270건 삽입 / 22개 컬럼 / 100%, Duration 15.9~19.3초
             Max Memory 278MB (1024MB 중)
```

**NAT 삭제 전후로 2회 수행**했다. 삭제 전에는 NAT 우회가 가능해 엔드포인트 검증이 되지 않으므로,
삭제 후 재수행으로 SQS·S3 엔드포인트 경유를 실증했다.

### 퍼블릭 서브넷 이동 보안 검증

- `finance-ecs-sg` 의 `0.0.0.0/0` 인바운드 **0건** (ALB SG 단일 규칙)
- 태스크 퍼블릭 IP `54.180.158.64:8080` 직접 접근 → **TcpTestSucceeded = False**
